## 2. MCP Server 架构现状（v0.2.0 = v1.0）

### 双二进制架构

```
myshelltool.exe          # GUI（windows 子系统），人用
myshelltool-mcp.exe      # MCP Server（console 子系统），AI 用，被 Claude Desktop 拉起
```
共享 `myshelltool_lib`（cdylib + rlib）。

### v1.0 模式：独立会话

MCP 进程自己 headless 建连（`HeadlessSshClient`），**不复用 GUI 会话**。
- host key 未信任直接拒绝（D4 安全门）
- 仅支持密码/私钥/keyboard-interactive 密码类 prompt（MFA 不支持）

### MCP 三原语实现位置

| 原语 | 文件 | 内容 |
|------|------|------|
| Tools | `src-tauri/src/mcp/tools.rs` | 9 个（7 只读 + 2 高危）|
| Resources | `src-tauri/src/mcp/resources.rs` | 4 个（3 静态 + 1 template）|
| Prompts | `src-tauri/src/mcp/prompts.rs` | 3 个诊断 prompt |
| 审批 | `src-tauri/src/mcp/approval.rs` | 三层审批 + 三段式拒绝 |
| Server | `src-tauri/src/mcp/server.rs` | rmcp ServerHandler + stdio serve |
| 危险命令 | `src-tauri/src/dangerous_commands.rs` | 16 条正则（GUI+MCP 共享）|

## 3. 下一轮迭代：v0.3.0（MCP v1.1）

### 核心目标

**named pipe 桥接**：MCP 进程不再独立建连，而是通过 Windows named pipe 连接 GUI 进程，复用 GUI 已建立的 SSH 会话。

这是用户在 v0.2.0 开发中提出的架构直觉——「既然 GUI 已经持有会话，为什么 MCP 还要再连一次」。v1.0 的独立会话是为规避 AppHandle 改造做的妥协，v1.1 用符合 MCP 协议的方式兑现这个直觉。

### 架构图（v1.1 目标）

```
Claude Desktop（父进程）
   └── myshelltool-mcp.exe（子，stdio）  ← Claude 必须是父进程（协议约束）
          │
          │ Windows named pipe: \\.\pipe\myshelltool-mcp
          ▼
myshelltool.exe（GUI）
   └── AppState（持有 SshSessionManager + 已建立的 SSH 会话）
       MCP 通过 pipe 复用会话，不再独立建连
```

### v1.0 vs v1.1 对比

| 维度 | v1.0（已实现）| v1.1（待实现）|
|------|--------------|--------------|
| 会话来源 | MCP 独立建连（HeadlessSshClient）| 复用 GUI 会话（named pipe）|
| 审批 | 进程内拒绝（isError）| GUI 三段式弹窗人工确认 |
| 删除操作 | 默认拒 | GUI 弹窗确认 |
| 数据一致性 | 各自读文件（有竞态风险）| 共享 GUI 内存（单一数据源）|
| host key | 仅服务已信任资产 | 复用 GUI 已完成的信任 |
| MFA | 不支持 | GUI 弹窗可收集（v1.1 可能支持）|

### 实施步骤（M7-M8，估时 3-7 天）

1. **M7：named pipe 基础设施**
   - GUI 主进程 setup hook 启动 pipe server（`tokio::net::windows::named_pipe`）
   - pipe server 持有 `Arc<AsyncMutex<SshSessionManager>>`（已具备，`AppState.ssh_sessions`）
   - MCP 子进程作为 pipe client 连接
   - 定义 pipe 协议（JSON：请求/响应，含 tool call 转发）

2. **M7：审批回路**
   - MCP 检测到高危命令 → 经 pipe 发审批请求到 GUI
   - GUI 触发 `GlobalModals.vue` 新增 `mcpApproval` 分支（三段式弹窗）
   - 用户决议经 pipe 回传 MCP
   - 前端 store 加 `resolveMcpApproval` action + workbench.js re-export

3. **M8：回归验收**
   - GUI 弹窗三段式显示 + 决议回传
   - 复用 GUI 会话执行命令（不再独立建连）
   - GUI 未运行时降级为 v1.0 独立模式

### 关键技术约束（v1.1 实施前必读）

- **stdio 协议约束**：Claude 必须是 MCP 的父进程。不能让 GUI 拉起 MCP（会破坏 stdio）。
- **cdylib 文件锁**：GUI 运行时锁住 `myshelltool_lib`，MCP 无法重建。开发期需先停 GUI。
- **AppHandle 改造**：v1.1 要让 MCP 经 pipe 访问 GUI 的 `AppState`。v1.0 推迟的 `Option<AppHandle>` 改造（ssh.rs 的 6 处 emit 点）在 v1.1 会重新评估，但方案从「改 app 类型」转为「经 pipe 转发」，影响面更小。

## 6. 已知问题与注意事项

### 网络问题

- GitHub push 可能因网络问题失败（SSL_ERROR_SYSCALL）。git 代理配置已清空，若需要可设 `git config http.proxy http://127.0.0.1:7890`。
- 用户的代理软件 SSRUNCore 在 7890 端口，但上游节点可能不稳定。

### PowerShell 编码陷阱（重要）

- **不要用 PowerShell `Set-Content` 写含中文的文件**——会用 GBK 编码破坏 UTF-8。改用 Edit/Write 工具。
- **不要在 PowerShell 里用 `curl`**——它是 `Invoke-WebRequest` 的别名，参数不兼容。用 cmd 或 `curl.exe`。

### Windows + Tauri cdylib

- GUI 和 MCP 共享 `myshelltool_lib`（cdylib），**不能同时编译**（文件锁）。
- 开发期用 `npm run dev:all`，它会检测锁并提示。
- 发布构建前必须停掉所有 myshelltool 相关进程。

### MCP 数据目录

- GUI 数据目录：`%APPDATA%\com.redtei.myshelltool\`（Tauri 用 identifier 命名，不是 productName）
- MCP 读取同目录（`lib.rs::mcp_data_dir()`），可用 `MYSHELLTOOL_DATA_DIR` 环境变量覆盖
- 之前曾因目录名写错（`myshelltool` vs `com.redtei.myshelltool`）导致 MCP 读假数据，已修复
