## 1. 域概述与现状小结

### 1.1 域对象与任务链

本域用户反复处理的对象：**当前目录里的一批文件条目**。一次处理的动作链：浏览目录（面包屑/上级）→ 选中条目（单选/多选）→ 传输（上传/下载/目录整传）→ 处理同名冲突（三选）→ 跟踪进度与处置结果（取消/重试）。传输是该域的核心动作，浏览是它的前置，状态栏胶囊是传输状态的常驻聚合出口。

主任务链五步（继承全局 brief，本域承担第 4、5 步）：
1. 找到主机（资产树，连接域）；
2. 建立连接（host key 闸口，连接域）；
3. 终端操作（终端域）；
4. **文件传输**：FileSurface 本地|远程双栏，拖拽/右键上传下载，同名覆盖先走确认弹窗，可取消。完成判定：TransferDrawer 行级进度到「已完成」+ success toast（语料 `docs/UI设计token语料.md` §5 拖拽状态机 0-5）；
5. **看状态**：状态栏 28px 聚合（传输胶囊显示活跃传输计数，`WorkbenchShell.vue:69,:427-431`）。

三条失败路径中本域承担一条，以代码锚点定格：**传输失败** = error 级 toast 含原因（`transferQueueOps.ts:186-189`，带「重试」action）+ 队列「已失败」tab 保留可重试（`TransferDrawer.vue:53,:197-206`）；**取消 ≠ 失败**（cancelled 计入「已完成」tab，行内药丸显示「已取消」，`TransferDrawer.vue:33-36,:52`、`files.ts:189-193` 注释，AGENTS.md §9 红线）。

### 1.2 现状小结（引诊断 summary + 本轮复核修正）

诊断小结（引）：骨架为 FileSurface（默认远程全宽、view-pills 切双栏、两级右键菜单、OS 拖入整面 + 栏间拖拽双通道）→ FileColumn 按 kind 复用本地/远程单栏（Header 面包屑+过滤浮窗 / Columns 排序表头 / List 行网格），传输面独立三件：TransferDrawer 四 tab 抽屉、UploadProgressStrip 批次条、GlobalModals 冲突三选弹窗；lib 层（fileOverwrite/dirTransfer/transferConcurrency）fail-closed 与注释质量高。工程纪律好：全域无 `transition:all`、无 hover 盒模型改动、无硬编码色/z-index、空态四分支齐全、关闭≠取消语义严格分离；问题集中在反馈可见性（选中计数被 display:none 藏死、busy 期间拖入静默）、键盘可达性（行不可聚焦 + 快捷键 hover 门控）、覆盖按钮未用 danger，以及少量死代码/重复实现。

**本轮复核对诊断的两处修正**（复核命令见对应行号，均已在源码确认）：

1. **「队列只增不减」不成立，问题方向相反**。`pruneFinishedTransfers`（`transferQueueOps.ts:90-96`）在每个传输完成（`transferQueueOps.ts:86`）与出错（`:107`）时自动触发，清掉 `finishedAt` 早于 60 秒前的全部终态记录；`fileTransfers.ts:268,:290,:424,:451,:470` 另有 5 处批次内调用。真实行为：终态记录只保留 60 秒窗口，随后被下一次 prune 清除。真实设计问题因此反转为：失败记录（含原因文案与重试入口）60 秒后自动消失，与 00 §3.6「需用户行动的错误必须常驻到被处理」相抵触；「已失败 tab 保留可重试」的实际承诺只有 60 秒。诊断中「无用户手动清理/单行移除入口」部分属实（grep `clearCompleted|clearFinished|removeTransfer|dismissTransfer` 全库无命中，本轮执行）。
2. **覆盖按钮样式调整不破坏既有测试**。`tests/ui-ipc-flows.mjs` 对冲突三选的驱动全部走 store 层（`window.__myshelltool.files.confirmFileOverwrite()`，:427,:524 等 6 处），唯一 DOM 点击 `#modalPrimary`（:854）属于 assetEditor 弹窗，与覆盖按钮无关；覆盖按钮现带 `id="modalPrimary"`（`GlobalModals.vue:467`），改 class 保留 id 即零测试影响。

另核实两处诊断未覆盖的现状事实，登记供后续决策：远程列表头常驻弱提示「右键查看更多操作」（`FileSurface.vue:420`）与语料 L4「常驻教学文案」禁令存在张力（S2 阶段注释明言「常显，最少打扰」，是有意决策，见 §7 openQuestions）；字节格式化两处实现均无 GB 档，>1 GiB 显示「1536 MB」（`fileColumnUtils.ts:45-50`、`transferUtils.ts:75-80`，格式细节随 A6 记录）。

## 3. 布局骨架决策

**页面类型：workspace**（三类判定依据 `design-craft-layout-rhythm/references/布局适用范围.md`「workspace：围绕工作对象组织一种主骨架，重复行、固定密度与分栏是允许且常常必要的；检查对象处理路径、信息可比性、滚动区、固定操作和空/满载状态」）。本域围绕「目录内容」这一反复处理对象组织固定骨架，文件行是重复条目、表格密度恒定、双栏对开是传输工作流的必要形态——三个 workspace 判据全部命中；非 focused（不是单表单/短落地页）、非 long-form（无叙事区块）。

**对象声明**（console 技能第 0 步格式）：用户在这一屏反复处理的对象是「当前远程（或本地）目录里的文件条目」；每天高频次处理（批次上传/下载 + 逐文件浏览编辑）；一次处理的动作链 = 浏览 → 选择 → 传输 → 冲突三选 → 跟进度/处置。这个对象缺的信息（进度、冲突原因）由 UploadProgressStrip 与冲突弹窗补齐，不需要跳页。

**骨架选择**：主骨架 = **双栏对开表格**（现有 `file-dual` grid：`1fr 1px 1fr`，仅远程时塌缩为 `1fr`，`FileSurface.surface.scss:65-76`）。它对应 console 十布局中的 #8「目录树型」的扁平变体——层级导航由面包屑承担（`buildPathCrumbs`，`fileColumnUtils.ts:108-150`）而非左树，因为 SSH 运维场景按绝对路径深潜比逐级树展开更快，且语料 L3 既成规格就是「本地|远程双栏；路径面包屑」。TransferDrawer、UploadProgressStrip、冲突弹窗均为附属浮层，不构成第二种主骨架；一屏一种主骨架规则满足。

**密度**：同屏单一紧凑档（00 §2.4）。文件表格行 `min-height: 30px`（`FileColumnList.vue:236`）、表头 30px（`FileColumnColumns.vue:55`）、栏头 34px（`FileColumnHeader.vue:218`）、file-header 32px（`FileSurface.surface.scss:14`）——均在语料 P6「列表行 28-32px」区间内，无需覆盖登记。控件高沿 AppButton sm≈24/md≈28 全局档。

**与整壳的关系**：文件区是五区域 grid 的 main 区底部一块（grid-template-areas `'titlebar titlebar titlebar' / 'sidebar main right' / 'statusbar statusbar statusbar'`，`workbench-shell.scss:8-11`），上方是终端 hero（00 §2.6 特色一）。本域不改整壳骨架。

### 4.8 目录整传边界反馈 — dirTransfer（复验缺口补定格）

页面类型：无独立界面——目录整传的反馈全部经既有通道呈现（announce toast / TransferDrawer 行 / UploadProgressStrip 批次态），本节只定格两条 fail-closed 上限触发时的反馈契约，不新造容器。本节补一致性复验指认的覆盖缺口（`dirTransfer.ts` 原仅 §1.2 一句带过）。

触发点与现状（代码锚点）：树收集阶段 `assertCollectLimits`（`dirTransfer.ts:117-124`）执行两条上限——递归深度 >16（`MAX_TREE_DEPTH`，`:26`，对齐 MCP recursive_remove_dir 的 16）与单批文件数 >2000（`MAX_TREE_FILES`，`:28`），超限即抛错中止整批（fail-closed，不静默截断）。异常上抛到入口 catch 后以 error 级 announce 呈现（上传 `:360`、下载 `:451`）。**时序保证**：收集先于建目录（上传 `walkLocal` 在 `:316`、`ensureRemoteDir` 自 `:326` 起；下载 `walkRemote` 在 `:400`、`ensureLocalDir` 自 `:402` 起），超限中止时远端/本地均无任何改动——文案可如实声明「无副作用」。

四要素落位（对照 00 §3.6）：现状文案有「发生了什么」（超限项+路径）与「影响」（整批已中止），缺「下一步」。定格补全（上传/下载同构，仅方向词不同）：

| 触发 | 定格文案 | 要素落位 |
|---|---|---|
| 深度超限 | 「目录上传中止：<路径> 层级超过 16 层上限。整批未开始传输，远端无改动。请拆分目录树后分批重试。」（下载侧为「下载中止…本地无改动」） | 发生了什么=超限+路径；影响=整批中止且无改动；原因=层级事实；下一步=拆分重试 |
| 文件数超限 | 「目录上传中止：<路径> 文件数超过 2000 上限。整批未开始传输，远端无改动。请减少文件数或分批重试。」（下载侧同构） | 发生了什么=超限+路径；影响=整批中止且无改动；原因=数量事实；下一步=减量或分批 |

呈现层级：维持单条 error announce 为第一出口——收集阶段批次尚无队列行，抽屉/进度条无落点，不在无行可显时造骨架容器；收集开始即有「正在扫描…」进行态提示（`:314`/`:398`），不另造 loading。「取消≠失败」口径不变：`已取消目录下载：<名>（已下载 N 个，剩余 M 个未下载）`（`:432-438`）四要素齐，登记为全域取消文案范本。符号链接跳过维持完成摘要后缀如实呈现（`symlinkNote`，`:226-229`），不单独打断。

空态四分落位（对照 00 §3.5）：目录整传不产生新空态——四类均不适用（动作被拒属错误路径，非空态）；此即 00 §3.5 在本模块的落位结论：无新增消费面。

非目标：不改 `MAX_TREE_DEPTH`/`MAX_TREE_FILES` 数值与 fail-closed 语义（判据属 lib 层权威，AGENTS.md §9 目录整传边界条）；不把超限中止改造成自动分批续传（涉产品决策，如需要应另立任务）。

验收：两处 throw 文案与模板逐字一致后，构造 >16 层目录与 >2000 文件目录各一次，确认 announce 文案、error 级别与「无改动」声明成立（`test:ui` ipc-flows 可挂 mock 断言）。
