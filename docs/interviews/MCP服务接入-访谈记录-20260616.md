## Round 1 | Intent Clarity | 歧义 100% → 65%

**目标**：锁定最根本的「为什么」。

**问题**：你希望 AI / 外部工具通过 MCP 调用 myshelltool 时，最主要的场景是哪一个？
- A. AI 运维助手（你在 Claude 里说「看看 web-01 的 CPU」，AI 调用 myshelltool 去查）
- B. 无人值守自动化节点（myshelltool 作为可被 CI/脚本调用的运维执行节点）
- C. AI-native 客户端（myshelltool 自己变成能听懂自然语言的客户端）
- D. 生态差异化卖点

**用户回答**：主要是第一和第二，不太理解第三是什么意思，需要解释一下。第四点本身就在第一和第二中了。

**架构师补充解释**（选项 3 含义）：
- 选项 3 = 给 myshelltool 自己加对话框，MCP 在内部做胶水，大模型被 myshelltool 集成进来
- 对比三个选项本质：选项 1 大模型在 Claude 里 / 选项 2 大模型在 CI / 选项 3 大模型在 myshelltool 内部

**结论**：用户选 1+2，myshelltool 是**被动服务方**。跳过选项 3 省掉一整层 LLM 集成。选项 4 是 1/2 自然结果。

## Round 2 | Outcome Clarity | 歧义 65% → 55%

**目标**：会话从哪来（决定架构骨架）。

**问题**：AI 调用 myshelltool 时，它操作的 SSH 会话从哪里来？
- A. 复用 GUI 会话（AI 只能操作已手动连上的会话，GUI 关了 AI 没手脚；安全最佳）
- B. 独立建立会话（MCP server 自己用资产库凭据建连，可无人值守；凭据被 AI 间接使用）
- C. 两模式可配（默认复用，特定资产开「AI 可独立连接」开关；最灵活最复杂）

**用户回答**：两模式可配。

**结论**：选 C。同时覆盖白天陪同时（模式 A）和夜里/CI（模式 B）。但带来 stdio/SSE 架构分叉的关键决策点，需 R3 施压。

## Round 3 | Scope Clarity + Contrarian | 歧义 55% → 50%

**施压点**：两模式可配 + stdio 与 SSE 架构约束相反，同时做会得到四不像。

**问题**：MCP 传输层，以哪个为主力？
- A. stdio 为主（Claude Desktop/Cursor 本地拉起，复用 GUI 会话需额外 IPC）
- B. SSE 为主（常驻 HTTP 服务，会话复用简单，多客户端共享，适合自动化）
- C. 听你推荐

**用户回答**：听你推荐。

**架构师推荐**：**stdio 为主力，SSE 推 v2**。
依据三维度：
- 主流生态：Claude Desktop/Cursor/Cline 默认 stdio
- 单机个人使用：stdio 无监听端口
- 安全风险最低：stdio 零远程攻击面

**架构决策（替用户定）**：不做独立二进制 `myshelltool-mcp.exe`，而是 `myshelltool.exe --mcp-stdio` 子模式。会话复用走 named pipe IPC。
> ⚠️ 此决策后被核查修正（见 Round 9 后的核查发现）：windows_subsystem 链接时定死，必须双二进制。

## Round 4 | Constraint Clarity（安全红线）| 歧义 50% → 42%

**目标**：整个项目风险最高的一题——SSH 执行权交给 AI 的审批策略。

**问题**：AI 通过 MCP 调用 SSH 时，命令执行的安全审批策略用哪种？
- A. 逐次人工审批（每次弹 GUI 确认）
- B. 只读自动 + 写操作审批
- C. 白名单准入（按资产配置允许的命令前缀）
- D. 不拦截

**用户回答**：使用预设+配置+审核的制度，高危命令必须经过手工确认，并且明确告知用户该条命令会产生什么后果。

**架构师结构化**：用户给出比单选更成熟的组合策略，三层模型：
- L1 预设白名单（配置好的安全只读命令）→ 自动执行
- L2 配置黄名单（用户在资产配置里加的「可接受」命令）→ 自动执行 + 事后日志
- L3 高危审批（不在白/黄名单，或匹配危险模式）→ 必须人工确认 + 显式说明后果

对应复用：`dangerousCommands.js`（正则库）+ `GlobalModals.vue`（弹窗中枢）。

## Round 5 | Ontologist（追问本质）| 歧义 42% → 38%

**施压点**：「高危」判断由谁做？
- 规则匹配追不上 AI 语义逃逸（rm -rf 拆成 rm -rf /var + /log/*）
- AI 自评不可信（被授权方自评自己）

本质问题：要拦的不是「命令」，是「意图」。

**问题**：命令审批拦截在哪一层？
- A. 命令层拦截（黑/白名单）
- B. 意图层拦截（AI 声明）
- C. 二级 AI 评估

**用户回答（首次）**：意图层拦截（AI 声明）。
**用户反馈**：Round 5 重新选，点错了。

**重新发问**（Round 5 重选版）。

**用户回答（重选）**：第一和第二都很棒，采用第一的形式，并且加入第二的弹窗显示三样的方法。

**架构师结构化**：聪明的组合——命令层兜底 + 意图层呈现。
| 机制 | 作用 | 触发 |
|------|------|------|
| 命令层正则匹配（黑+白+默认拒）| 决策器 | 命中白→自动；命中黑/未识别→弹窗 |
| 弹窗三段式（意图+命令+后果）| 辅助决策 | 触发弹窗时附带 |

把「意图声明」降级为信息展示而非决策器，避开「AI 评 AI」信任陷阱。defense in depth。

## Round 7 | Simplifier | 歧义 35% → 28%

**施压点**：保留范围里成本不对等。模式 B 工程成本极高（凭据注入 + host key 自动策略 + 多进程并发仲裁），且与「高危审批需人在场」**逻辑自相矛盾**。

工程成本量化：
- MCP Tools：中（复用 25 个 Tauri 命令）
- 模式 A：中（named pipe + 协议适配）
- Resources/Prompts：低
- 模式 B：高（三项子问题任何出错都是安全事故）

**问题**：鉴于模式 B 与高危人工审批逻辑自相矛盾，第一版如何处理模式 B？
- A. 模式 B 推到 v2（推荐）
- B. 第一版保留但限制只读
- C. 完全保留

**用户回答**：模式 B 推到 v2（推荐）。

**结论**：v1 范围收敛为 MCP stdio server + 模式 A + Tools/Resources/Prompts + 三层审批。逻辑自洽（审批要求人在场 = 模式 A = GUI 复用）。

## Round 9 | Pressure Pass（回访 R2）| 歧义 22% → 18%

**回访点**：Round 2「两模式可配」经 R7 修正为「v1 模式 A，v2 模式 B」。验证隐藏假设——Claude 拉起 MCP server 但 GUI 没运行时怎么办？

**问题**：Claude 拉起 MCP server 但 myshelltool GUI 没运行时，AI 调 SSH 会话该怎么办？
- A. 报错提示启动 GUI
- B. 自动拉起 GUI
- C. 降级只读

**用户回答**：尝试几次拉起 GUI，如果还未果就降级只读。

**架构师结构化**：优于三选项的组合策略——带重试的优雅降级：
```
AI 调 SSH 会话
  ├─ GUI 在线? → 复用会话执行
  └─ GUI 不在线?
       ├─ 重试拉起 GUI（最多 N 次，间隔递增）
       │    └─ 拉起成功? → 等 pipe 就绪后执行
       └─ 仍未果 → 降级只读模式
            └─ AI 只能调本地数据类工具，不调 SSH
            └─ 返回明确错误「SSH 会话不可用，已降级为只读」
```

弹性设计：避免「报错就死」僵硬 + 避免「无限等 GUI」死锁 + 保留「至少返回点东西」可用性。

## 访谈后核查发现（非访谈轮次，但影响架构）

**Explore agent 核查事实（2026-06-16）**：
1. `main.rs:1` 已有 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` → release 子进程 stdin/stdout 不可用
2. Claude Desktop 拉起 MCP server 靠 stdin/stdout 读 JSON-RPC → 读不到 = MCP 协议直接失败
3. subsystem 是链接时属性，运行时 argv 判断已晚，**无法纯运行时切换**

**架构修正**（仍兑现访谈所有决策）：
| 访谈决策 | 原架构 | 修正架构 | 兑现 |
|---------|-------|---------|------|
| stdio 主力 | `--mcp-stdio` 子命令 | 双二进制（GUI + console MCP exe）| ✅ |
| 模式 A 复用 GUI 会话 | 同进程复用 | named pipe 桥接（MCP 子进程连 GUI 进程）| ✅ |
| GUI 未运行弹性降级 | 同进程检测 | MCP 子进程连 pipe 失败→重试拉起→只读 | ✅ |
| 三层审批+三段式弹窗 | 同进程弹窗 | 审批经 pipe 送 GUI 弹 mcpApproval modal | ✅ |

唯一新增工程项：tokio named pipe（项目已用 tokio，原生支持，零新依赖）。

## 关键决议清单（供实施继承）

1. **核心意图**：AI 运维助手 + 自动化节点（v2）
2. **传输主力**：stdio（SSE 推 v2）
3. **会话模式**：v1 模式 A 复用 GUI；v2 模式 B 独立建连
4. **二进制形态**：双二进制（核查修正）
5. **审批策略**：三层（白/黄/默认拒）+ 三段式弹窗（意图+命令+后果）
6. **审批本质**：命令层兜底 + 意图层呈现（决策由规则做，意图仅辅助）
7. **范围**：v1 = Tools+Resources+Prompts + 模式 A；v2 = 模式 B + SSE
8. **降级**：GUI 未运行 → 重试拉起 → 只读
9. **决策授权**：重大决策需候选+推荐+依据
10. **残余风险**：提示词注入（行业级未解）必须留档
